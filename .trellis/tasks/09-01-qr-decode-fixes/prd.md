# QR decode accuracy and code quality fixes

## Goal

修复"框选了二维码却提示未发现二维码"的偶发失败,并清理上一轮代码分析发现的质量问题。父任务 `08-08-tampermonkey-qr-scanner` 的 R1–R4 需求不变,本任务只改实现。

## Confirmed Facts

以下事实均在本仓库中实测确认,不是推断:

- **选区坐标被丢弃。** `captureVisiblePage(rect)` 只用 `rect` 筛选与之重叠的候选元素,`captureCandidate` 随后解码的是**整个元素**。用户框住的区域从未参与裁剪,选区对送入解码器的像素没有任何影响。
- **两个解码器是同一个库。** `qr-scanner@1.4.2` 的 devDependencies 含 `jsqr-es6`,其 legacy 构建内部就是 jsQR。`decode.js` 的"Worker 优先 + 主线程回退"不是两次独立算法机会,是同一算法跑两遍。
- **像素闸门在最需要时关闭回退。** `MAX_MAIN_THREAD_PIXELS = 1200000`。实测:1920×1080 = 2073600 像素,已超闸门,jsQR 那一路直接跳过。图越大越难解,而恰好此时没有第二次尝试。
- **降采样会毁掉码的密度。** `MAX_RASTER_SIDE = 2048`。实测:4000×3000 的图里一个 200×200 的码被压到 102px;3000×2000 里压到 137px。高密度码(version 10+)在这个尺寸下解不出来。
- **从不尝试反色。** jsQR 支持 `inversionAttempts`,当前调用未传该选项,走默认值。深色背景上的浅色码会失败。
- **解码耗时随像素数超线性增长,且在主线程。** 实测 jsQR(Node,`dontInvert` / `attemptBoth`):
  | 输入 | dontInvert | attemptBoth |
  |---|---|---|
  | 512×512 | 63ms | 85ms |
  | 1024×768 | 177ms | 367ms |
  | 1920×1080 | 813ms | 1.9s |
  | 2048×1536 | 4.3s | 8.0s |
  | 3000×2000 | 12.2s | 24.1s |

  当前最多遍历 8 个候选,最坏情况会让页面冻结数分钟。`MAX_MAIN_THREAD_PIXELS` 闸门原本正是在挡这个,不能简单删除。
- **产物体积含重复的 jsQR。** `jsqr` 未压缩 251 KiB,`qr-scanner` legacy 构建 68.5 KiB(内部同样是 jsQR),其自带 worker 仅 43 KiB。dist 共 447 KiB,两份同算法是主因。
- **`.git` 目录为空**(只有 `.` 和 `..`),所有 git 命令报 `not a git repository`。已确认无可恢复历史。
- **Base64 实现有两份副本。** `src/base64.js` 与 `tests/qr.test.mjs` 各自定义 `base64Encode`/`base64Decode`。测试验证的是它自己的副本,不是产品代码。
- 现状:17 个测试全部通过;`src` 共 842 行;产物 447 KiB。

## Requirements

### R5. 选区必须真正参与解码

- 送入解码器的像素必须裁剪到用户选定的矩形与目标元素的交集,按元素自身的显示缩放换算回原始像素坐标。
- "扫描当前页"传入整个视口矩形,行为等价于现状,不得因裁剪逻辑而回退。
- 元素被选区部分覆盖时,只解码覆盖部分;完全覆盖时解码整个元素。

**验收:** 单元测试覆盖 CSS 显示尺寸与原始像素尺寸不一致时的坐标换算(含 `object-fit` 造成的非等比情况须显式处理或明确记录为不支持)。

### R6. 解码前保证像素质量

- 像素闸门**保留但改为在裁剪之后判断**。裁剪把典型输入从整图降到选区尺度,绝大多数情况下裁剪后即可通过闸门,不再因原图大而丧失回退机会。
- 裁剪后区域小于解码器可靠工作的下限时,放大而非缩小(关闭平滑,避免插值模糊破坏模块边缘)。
- 降采样上限只应作用于**未裁剪**的输入以控制内存,不得作用于已裁剪到选区的小块。
- 反色解码按需启用:先 `dontInvert`,未解出且该块足够小时再试反色。不对大块无条件付翻倍成本。

**验收:** 单元测试断言闸门作用于裁剪后尺寸而非原始尺寸;断言小块输入被放大而非缩小;断言反色仅在第一轮失败后触发。

### R11. 扫码性能可预期

- 单次扫码的主线程阻塞必须有上界,不得让页面出现秒级冻结。
- 优先使用浏览器原生 `BarcodeDetector`(若可用):它是独立实现,通常有硬件加速,比 jsQR 快一个量级。
- 候选遍历必须有整体时间预算,超预算即停止并如实反馈,而非无限尝试 8 个候选。
- 候选排序应让最可能命中的元素先解码,配合已有的提前退出。
- 单个候选的解码成本在超过闸门时应被跳过或降级,不得阻塞。

**验收:** 单元测试断言超时预算生效并产生可区分的反馈;断言 `BarcodeDetector` 可用时被优先调用;断言超闸门的候选不会进入主线程解码。

### R12. 控制产物体积

- 消除同一解码算法的重复打包(`jsqr` 与 `qr-scanner` 内部 jsQR)。
- 记录改动前后体积,体积不得增长。

**验收:** `npm run build` 后产物体积不高于改动前的 447 KiB,并在任务中记录实际数值。

### R7. 失败反馈必须可区分

- 区分"读到了像素但没解出码"与"根本读不到像素"(跨域受限、CSS 背景、跨域 iframe),分别给出不同提示。
- 不得在读不到任何像素时报"未发现二维码"。

**验收:** 状态机测试覆盖两类失败路径产生不同 message。

### R8. Base64 单一实现

- `base64Encode`/`base64Decode` 抽到独立模块并导出;`src/base64.js` 与测试都从该模块导入,消除副本。
- 测试必须验证产品代码,而非测试内的副本。
- `src/base64.js` 的代码风格与其余文件统一(分号)。
- 成功态与错误态不再复用同一 DOM 元素靠 inline style 切换语义。

**验收:** 仓库中 `base64Encode` 只有一处定义;现有 8 个 base64 测试全部仍通过。

### R9. 修复仓库版本控制

- 重新初始化 git 仓库,将现有代码作为首个提交。
- 提交前确认 `node_modules` 与 `dist` 的忽略策略。

**验收:** `git log` 有可读历史;`git status` 干净。

### R10. 文档与注释诚实

- `decode.js` 中声称"worker already missed"的注释须改为反映真实行为(同一库跑两遍)。
- README 说明 `@connect *` 配合 `GM_xmlhttpRequest` 的授权范围与用途。
- README 的"已知限制"与实际代码行为一致。

## Non-Goals

- 不引入第三方独立解码库(体积代价大)。浏览器原生 `BarcodeDetector` 不算此列——它零体积成本。
- 不把 jsQR 移进 Web Worker。Worker 能消除主线程阻塞,但 userscript 环境下 Worker 构造受页面 CSP 限制、且需把解码库内联为 blob,复杂度高。本轮先用"裁剪 + 闸门 + 时间预算"把成本压到可接受范围;若仍不足另立任务。
- 不实现多码同时识别。
- 不支持 CSS 背景图与跨域 iframe 内的二维码(维持现有限制并如实说明)。
- 不改动 `@match` 范围或菜单入口交互。
